# 티켓 동기화 대조 (sync-ticket)

## 목적

Notion "Run패스포트 Develop" DB의 담당 영역=프론트엔드 뷰와 로컬 `ai/develop-ticket.md`를
대조한다. **로컬 파일을 자동으로 덮어쓰지 않는다** — 불일치 리포트만 만들고, 실제 반영
(로컬 파일 수정 / Notion 상태 갱신)은 매번 사용자 확인을 받은 뒤 1건씩 처리한다. 자세한
배경은 `ai/response.md`("요청 응답: Notion 티켓 동기화 관리 방식") 참고.

## 1단계: Notion 조회

- 데이터 소스: `collection://2c59c9e2-d478-828c-978b-07827b6aa116` ("Run패스포트 Develop")
- SQL 조건: 담당 영역(정확한 속성명·옵션값은 실행 시점에 스키마로 확인 — 추측하지 않는다)이
  '프론트엔드'인 행만. 예상('영역'='프론트엔드')과 다르면 실제 값을 채팅에 보여준 뒤 그 값
  기준으로 진행한다.
- 가져올 컬럼: `url`, `이름`, `상태`, `우선순위`, `마일스톤`, `date:기간:start`, `date:기간:end`
- 마일스톤 이름이 필요하면 `collection://5f49c9e2-d478-827d-8046-87cff91fa269` ("Run패스포트 마일스톤")도 함께 조회해서 relation URL을 이름으로 매핑

## 2단계: 로컬 조회

- `ai/develop-ticket.md`의 "## 티켓 목록" 섹션을 파싱한다. 이 저장소의 로컬 티켓 항목은
  `## [마일스톤명] 티켓명` 헤더 아래 `- 노션 링크: <URL>` / `- 상태: 시작전|진행중` /
  `- 세부 개발 항목: ...` 형식이다 (백엔드 저장소의 `(#ID)` 제목 표기 방식과 다름 — Android
  로컬 티켓은 이미 원본 Notion URL을 필드로 직접 들고 있으므로 그걸 매칭 키로 쓴다).
- 각 항목의 `노션 링크` 필드를 Notion 페이지 `url`과 대조해 매칭한다.
- `노션 링크: 없음`이거나 필드 자체가 없는 항목은 "노션과 연결 안 됨"으로 분류한다.
- 각 항목의 로컬 `상태`(시작전/진행중)도 함께 수집한다. 완료(DONE) 티켓은 로컬 규칙상 이미
  삭제되어 목록에 존재하지 않는다.

## 3단계: 대조

상태 매핑 규칙:

| Notion 상태 | 로컬 상태 |
|---|---|
| Backlog, To Do | 시작전 |
| In Progress | 진행중 |
| Review/Test | 진행중 |
| Blocked | 진행중 (단, 대조 결과에 "⚠️ Notion Blocked" 표시 — 로컬 티켓 포맷에는 별도 차단 상태 필드가 없음) |
| Done | 완료 (로컬 규칙상 삭제됨) |

다음 네 그룹으로 나눠서 정리한다:

1. **Notion에 있는데 로컬에 없음** — 특히 현재 진행 중인 마일스톤 주간(오늘 날짜 기준
   `기간`이 걸치는 마일스톤) 것을 우선 표시. Notion 상태가 Done이면 굳이 로컬에 없어도
   정상(완료 티켓은 로컬에서 지우는 규칙)이므로 제외.
2. **로컬에 있는데 노션 링크가 없거나 Notion에서 대응 페이지를 못 찾음** — 수동으로 추가된
   항목이거나 노션 쪽 URL이 바뀌었을 가능성. 어느 Notion 티켓을 가리키는지 사용자에게
   확인해야 함.
3. **같은 노션 링크인데 상태가 다름** — 매핑 규칙 기준으로 불일치인 것만.
4. **로컬 아카이브 누락** — `git log -p -- ai/develop-ticket.md`(또는 최근 커밋 diff)로
   "## 티켓 목록"에서 최근에 삭제된 항목이 있는지 확인하고, 그 티켓이
   `ai/ticket-archive.md`에 완료 메모로 남아있는지 대조한다. 완료 메모 없이 목록에서만
   사라진 티켓이 있으면 별도로 표시 — 실제 완료 근거(실행 로그/실기기 확인 등)가 있는지
   사용자에게 확인한 뒤에만 5단계로 넘어간다.

## 4단계: 출력

- 채팅에 표 형태로 요약만 출력한다 (파일로 저장하지 않는다 — 이건 read-only 진단이라 매번
  최신 상태를 다시 봐야 의미가 있음).
- 각 불일치 항목에 대해 "로컬에 반영할지 / Notion에 반영할지" 사용자에게 묻는다.
- 사용자가 승인한 것만:
  - 로컬 반영 → `ai/develop-ticket.md`를 Edit으로 수정. 신규 티켓은 기존 관례대로
    `## [마일스톤명] 티켓명` / `- 노션 링크` / `- 상태` / `- 세부 개발 항목`(노션 본문의
    작업 내용·완료 조건을 2~3개 실행 단위로 전개) / `- 완료 조건` / `- 선행 티켓` 형식으로
    추가한다. 기존 항목은 `노션 링크`나 상태 표기만 수정한다.
  - Notion 반영 → 티켓 1건씩 `notion-update-page`로 상태 변경. 여러 건을 한 번에 일괄
    변경하지 않는다.
  - 3단계 4번(로컬 아카이브 누락)에서 완료가 확인된 티켓 → `ai/ticket-archive.md`에 완료
    메모를 먼저 추가한 뒤, 5단계대로 Notion 아카이브 DB에도 페이지를 만든다.

## 5단계: 완료 티켓 Notion 아카이브 반영

`ai/ticket-archive.md`에 새 완료 메모를 추가했다면(4단계에서 확인됐거나, 사용자가 직접
요청한 경우), 같은 내용을 Notion "Run패스포트 티켓 아카이브" DB에도 페이지로 만든다.
CLAUDE.md의 "티켓/작업 관리 규칙" 절에 있는 요구사항과 동일 — 이 커맨드는 그 마지막 단계
(Notion 반영)를 실행하는 역할. 이 저장소(`ai/ticket-archive.md`)가 완료 메모의 원본(전문)이고,
Notion 페이지는 요약 + 관계형 링크만 담는다.

- 데이터 소스: `collection://28eb84c9-ac1d-4577-b1d3-013ece5f006e` ("Run패스포트 티켓 아카이브", 상위 데이터베이스는 `de1365c9-a4d3-4b51-8af2-f10ccaa43736`)
- 스키마: `이름`(title), `레포`(select — `runpassport-api` / `runpassport-android`), `완료일`(date, `date:완료일:start` + `date:완료일:is_datetime`), `티켓`(relation → `collection://2c59c9e2-d478-828c-978b-07827b6aa116` "Run패스포트 Develop")
- 페이지 생성 시:
  - `이름`: 로컬 티켓 제목 그대로 (`## [마일스톤명] 티켓명`의 티켓명 부분)
  - `레포`: 이 저장소 기준 항상 `runpassport-android`
  - `완료일`: 오늘 날짜
  - `티켓`: 로컬 항목의 `노션 링크` 필드 URL을 그대로 사용해 relation 연결 (Android 로컬
    포맷은 이미 원본 Notion URL을 직접 들고 있어 백엔드처럼 `(#ID)` 표기를 역으로 파싱할
    필요가 없다)
  - `완료 메모` 속성은 비워두고, 페이지 본문에 `## 목표` / `## 완료 메모` / `## 참고` 구조로
    `ai/ticket-archive.md`의 해당 항목 내용을 옮겨 적는다 (참고 절에 로컬 원본 경로
    `ai/ticket-archive.md` 명시)
- 한 번에 완료 티켓 1건씩만 페이지를 만든다 (여러 건 한꺼번에 만들지 않음 — 4단계와 동일한
  원칙).

## 금지사항

- 노션 원본 페이지/DB는 읽기 전용으로만 다룬다 (내용 수정, 속성/옵션 추가 금지). 상태 갱신은
  4단계에서 사용자가 승인한 항목에 한해서만 한다.
- 로컬에서 자동으로 항목을 삭제하거나 상태를 되돌리지 않는다 — 항상 사용자 확인을 받는다.
