# RunPassport 기능 명세

> 노션 '서비스 기획'(2026-08-02) / '기능 명세'(2026-08-06) 문서를 Android 앱 구현 관점으로
> 재해석해서 정리한 것. 노션 원본은 웹앱 체크인 방식으로 시작했다가 앱 + GPS 궤적 대조
> 방식으로 피벗했고, 이 문서는 **피벗 이후(최신) 방향만** 반영한다. 원본은 읽기 전용 —
> 이 문서를 갱신하려면 노션이 아니라 이 파일을 직접 고친다.

## 서비스 개요

RunPassport(런패스포트)는 전국 각지의 러닝 친화 코스(강변·해안·둘레길·도심공원 등)를 GPS로
인증하고 디지털 스탬프를 모아가는 상시형 러닝 플랫폼이다. 마라톤처럼 특정 날짜에 열고
닫는 행사가 아니라, 코스만 등록해두면 사용자가 원할 때 언제든 뛰고 인증할 수 있다. 날씨·
미세먼지 데이터로 오늘 뛰기 좋은 지역을 추천하고("러닝지수"), 코스 완주 시 지역 배지·
스탬프를 모아 지자체 리워드(쿠폰)로 교환할 수 있다. 러닝이라는 반복 행동을 매개로 특정
지역을 지속적으로 재방문하게 만들어, 지자체 입장에서는 생활인구 유입 데이터를 축적하고
정책 효과(코스 신설 근거, 이탈 지점 분석 등)를 측정하는 도구가 된다.

인증 방식은 최초 기획안(체크인: 출발/도착 지점 도달 시 자동 인증)에서 **GPS 궤적 대조**
방식으로 변경됐다. 코스 GPX와 사용자 궤적을 대조해 커버리지 비율(≥85%) + 진행 방향 +
페이스 범위(3~12분/km)로 완주를 판정하며, 이 판정은 클라이언트가 아니라 **서버가 최종
권위를 가진다** (앱이 "완주함"이라고 보내는 걸 그대로 믿지 않는다). 이 앱 저장소는 이
시스템의 Android 클라이언트만 다룬다 — 완주 판정 로직 자체와 공무원용 웹 대시보드는 별도
저장소(백엔드) 영역이다.

## 화면별 상세 명세

### 코스 목록 (지도 + 리스트)
- **진입 조건**: 로그인 후 홈 진입, 또는 하단 탭에서 진입
- **표시 데이터**: 지도 위 코스 마커, 코스명/거리/난이도/러닝지수 요약 카드 리스트
- **사용자 액션**: 지역/거리/난이도 필터, 코스 선택 → 코스 상세 이동
- **예외/에러 케이스**: 위치 권한 거부 시 지도는 기본 위치(전국)로 표시하고 "내 주변" 필터만 비활성화 — 크래시 없이 목록 자체는 항상 보이게 한다. 네트워크 실패 시 마지막으로 불러온 목록(또는 빈 상태 + 재시도 버튼) 표시.

### 코스 상세
- **진입 조건**: 코스 목록에서 코스 선택
- **표시 데이터**: 코스 GPX 경로 폴리라인, 코스 정보(거리/난이도/지형), 러닝지수
- **사용자 액션**: "러닝 시작" → 러닝 트래킹 화면 진입 (시작 전 코스 GPX 사전 다운로드)
- **예외/에러 케이스**: GPX 다운로드 실패 시 러닝 시작을 막고 재시도 안내 (오프라인 궤적 대조는 로컬 GPX가 있어야 가능하므로)

### 러닝 트래킹
- **진입 조건**: 코스 상세에서 "러닝 시작", 위치 권한이 승인된 상태
- **표시 데이터**: 실시간 이동 거리/시간/페이스, 현재 위치, (선택) 코스 경로 대비 진행 상황
- **사용자 액션**: 일시정지/재개/종료
- **예외/에러 케이스**: 위치 권한이 승인 전이면 트래킹 시작 자체를 막고 권한 요청 플로우로 유도(크래시 방지). 트래킹 중 앱이 강제 종료돼도 Foreground Service + Room 저장으로 진행 중이던 궤적이 유실되지 않아야 한다. GPS 신호 두절(터널/지방 오지) 시에도 앱이 죽지 않고 재수신 시 이어서 기록한다.

### 완주 결과
- **진입 조건**: 러닝 종료 → 궤적 업로드(WorkManager) → 서버 판정 완료
- **표시 데이터**: 판정 결과(성공/실패), 실패 시 사유(예: 커버리지 비율 미달, 페이스 범위 이탈), 기록 요약(거리/시간/페이스)
- **사용자 액션**: 결과 확인 후 스탬프 컬렉션/코스 목록으로 이동
- **예외/에러 케이스**: 네트워크가 없어 업로드가 지연되는 동안 "판정 대기 중" 상태를 명확히 보여주고, 무한 로딩처럼 보이지 않게 한다. 오프라인이었다면 네트워크 복구 시 자동 업로드 후 결과를 갱신한다.

### 스탬프 컬렉션
- **진입 조건**: 하단 탭 또는 완주 결과에서 이동
- **표시 데이터**: 지자체별 보유 스탬프 개수, 배지(예: "제주 해안 5코스 완주")
- **사용자 액션**: 스탬프 목록 탐색, 조건 충족한 배지 확인
- **예외/에러 케이스**: 스탬프 적립이 서버 반영 전이면 "반영 중" 상태로 구분 표시 (중복 카운트 방지)

### 쿠폰함
- **진입 조건**: 스탬프 조건 충족 → 쿠폰 발급 버튼, 또는 하단 탭에서 보유 쿠폰 확인
- **표시 데이터**: 보유 쿠폰 목록(지자체/매장, 유효기간, 상태: 미사용/사용됨)
- **사용자 액션**: 쿠폰 발급, 매장에서 "사용하기" → PIN 4자리 입력 → 사용 처리(되돌릴 수 없음)
- **예외/에러 케이스**: PIN 입력 화면은 실시간 시계 + 애니메이션으로 캡처(스크린샷) 방지. 사용 처리는 서버 트랜잭션으로 확정되므로, 네트워크 실패 시 "사용됨으로 착각하는 상태"가 생기지 않도록 서버 응답을 받기 전까지는 사용 완료로 표시하지 않는다.

## 클라이언트 기술 요구사항

- **위치 추적**: `FusedLocationProviderClient` + Foreground Service, 1~3초 간격 수집.
  `ACCESS_BACKGROUND_LOCATION`은 **신청하지 않는다** (Foreground Service 알림 방식이면
  불필요하고, 신청 시 Play 스토어 별도 심사로 승인이 몇 주 지연됨). 필요 권한:
  `ACCESS_FINE_LOCATION`, `ACCESS_COARSE_LOCATION`, `FOREGROUND_SERVICE`,
  `FOREGROUND_SERVICE_LOCATION`(Android 14+), 매니페스트에
  `android:foregroundServiceType="location"`.
- **노이즈 필터링 기준**: `accuracy > 25m` 포인트 폐기, 직전 포인트 대비 순간속도
  `> 8m/s` 포인트 폐기, 이동거리 `< 3m`이면 표류로 보고 누적하지 않음. 남은 포인트로
  Haversine 거리 누적. (이 필터링이 없으면 거리가 약 20% 부풀려짐)
- **부정 방지(클라이언트에서 할 수 있는 부분)**: `Location.isMock`으로 Mock location 앱
  차단. (Activity Recognition API 기반 `IN_VEHICLE` 탐지는 기능 명세에 언급은 있으나,
  노션 Develop DB의 현재 프론트엔드 티켓 목록에는 아직 없음 — 아래 "확인 필요" 참고)
- **완주 판정**: 클라이언트는 판정하지 않는다. 궤적을 서버로 업로드하면 서버가 커버리지
  비율/진행방향/페이스로 재계산해서 최종 판정한다.
- **오프라인 대응**: 러닝 시작 전 코스 GPX를 Room에 사전 다운로드. 궤적도 Room에 로컬
  저장 후, 네트워크 복구 시 WorkManager로 업로드.
- **배터리**: 1초 간격 HIGH_ACCURACY는 배터리 소모가 크므로 2~3초 간격을 쓰고, 최초 실행
  시 배터리 최적화 예외 요청 다이얼로그를 띄운다 (특정 제조사 기기의 자체 절전으로 인한
  "기록이 반만 남았다" 문제 예방).
- **지도**: 네이버 지도 Android SDK (폴리라인/경로 오버레이, 국내 도보길 렌더링 정확도
  이유로 채택).
- **로그인**: 카카오 로그인 SDK → 발급 토큰을 서버에 전달해 Supabase Auth 세션으로 교환.
- **백엔드 연동 API** (엔드포인트 상세 스펙은 백엔드 저장소 문서 기준, 이름만 나열):
  - 코스 조회 / 코스 상세(GPX 포함) 조회
  - 러닝지수 조회
  - 카카오 토큰 → Supabase 세션 교환
  - 궤적 업로드 & 완주 판정 결과 조회
  - 스탬프 적립 현황 조회
  - 쿠폰 발급 / 매장 PIN 사용 처리

## 확인이 필요한 부분

- 기능 명세 원문의 "부정 방지" 항목 중 **Mock location 차단**은 노션 Develop DB에
  티켓이 없어서(암묵적으로 위치 수집 구현에 포함된 것으로 보고) 위 기술 요구사항에
  포함해뒀습니다. **Activity Recognition API 기반 탈것 탑승 탐지**는 대응되는 프론트엔드
  티켓이 전혀 없어 이번 범위에 넣을지 이후 범위로 미룰지 판단이 필요합니다.
- 완주 판정은 서버 권위라고 명시돼 있는데, 노션 Develop DB의 "궤적 업로드 WorkManager
  연동"(ID 27) 선행 티켓이 "[BE] 궤적 업로드 API 뼈대 완료"로만 돼 있어 실제 판정
  엔드포인트/응답 스펙은 백엔드 쪽 문서를 확인해야 합니다 (이 저장소 범위 밖).
